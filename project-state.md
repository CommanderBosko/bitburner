**Root-caused and fixed the "$0 scripted income for hours" symptom on the fresh BN4 save (`c344ad9`, 2026-07-29) — two real bugs in `buildWorkingSet` (`controller.ts`), found by live-debugging rather than guessed at:** the user reported hacking scripts earning literally $0 over a 5h40m offline stretch despite 25 purchased 8GB servers and a dozen+ rooted, easily-affordable world targets sitting idle. Bisected via added `ns.print` diagnostics (see below) rather than assumption:
- `buildWorkingSet` debited its simulated RAM pool by `needed` — an unbounded demand *ceiling* (for a primed target, as many concurrent batches as timing allows, easily 10-100x one batch's real cost) — instead of `minUnit`, the candidate's actual one-batch/one-thread cost. This let an admitted candidate whose `minUnit` was cheap enough to pass the admission gate still zero out `poolRemaining` via its bloated `needed`, locking out every candidate after it.
- It also used `break` instead of `continue` when a candidate couldn't be funded — wrongly assuming RAM cost tracks the score-sorted candidate order. `candidates` is sorted by `maxMoney / minSecurity`, not thread cost, so one very expensive top-scored target (`omega-net`, needing 732 hack threads — 5-6x this fleet's entire ~230GB capacity) stopped the loop before it ever reached `foodnstuff`, `joesguns`, `n00dles`, and 10 other trivially-cheap rooted targets further down the same list.
- Root cause of *why* this was invisible: `controller.ts` never called `ns.disableLog`, so every `ns.*` getter (`getServerMaxRam`, `getServerUsedRam`, `getServerSecurityLevel`, `sleep`, etc.) auto-logged its return value — at ~24 hosts scanned every tick, that flooded the tail buffer and evicted the rarer, actually-useful diagnostic lines before they could be read. Added `ns.disableLog("ALL")` plus permanent `ns.print` diagnostics in `buildWorkingSet`/`dispatchBatch`/`dispatchTarget` so a future RAM-starvation stall is visible directly in the tail log without another round of live bisection.
- Confirmed fixed in-game: working set went from `[omega-net]` only to all 13 fundable candidates, and Active Scripts showed real `weaken.js` threads spread across the pserv fleet targeting `phantasy` (the highest-priority still-unprimed target) — expected/healthy saturation, not a bug. `omega-net` itself remains genuinely too big for the current ~230GB fleet and will keep failing to batch harmlessly until the fleet grows.
